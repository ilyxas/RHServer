# RHServer — план разработки

Сторона: rh-core, rh-agent, CLI `rhcore` / `rhpage`, скрипты установки. Что строим — `SPEC.md` v1.0; как работаем — `PROCESS.md`.
Исполнитель: агент сервера (Claude). Вторая сторона: агент iOS (Claude), репозиторий `ilyxas/RHClient`.

Статус документа: **черновик на утверждение Ильи.** Кода до утверждения нет.

## Как читать план

- Этапы — по SPEC §9. Для каждого: задачи, тесты, что нужно от iOS и в каком виде, какие **[проверить]** закрываются, где нужен Илья.
- **[утвердить]** — решение за Ильёй; до ответа эта часть не реализуется, остальная работа этапа идёт.
- **[проверить]** закрывается записью `docs/decisions/NNN-<тема>.md`: вопрос, вывод, источник (ссылка на документацию/код), дата. Если вывод расходится с SPEC — стоп по этому направлению и вопрос Илье.
- «Ждёт Илью» — шаги, которые может сделать только Илья; инструкции к ним даю полные и пошаговые, в треде и в PR.

### `contracts/`

Живёт в корне RHServer, веду я. Любое изменение — отдельным PR в RHServer, где агент iOS — ревьюер (его ок в PR обязателен), мержит Илья.

```
contracts/
  README.md                       # что где, как обновлять, правила версий
  CHANGELOG.md                    # каждое изменение с этапом
  MANIFEST.sha256                 # хеши файлов и корневой хеш для проверки копии у клиента
  api/openapi.yaml                # HTTP API (OpenAPI 3.1), x-rh-op / x-rh-key на каждой операции
  api/events.schema.json          # события WebSocket, discriminator "type"
  pages/rh.page.v1.schema.json    # SPEC §7.4 (этап 5)
  manifests/action.schema.json    # action.json (этап 5)
  manifests/data.schema.json      # data.json (этап 5)
  vectors/jcs.json                # этап 0
  vectors/ecdsa.json              # этап 1
  vectors/signed_requests.json    # этап 1
  vectors/request_build.json      # этап 1: тестовый ключ + поля → X-RH-Auth байт-в-байт
  vectors/server_sig.json         # этап 1
  vectors/ws_frames.json          # этап 3: подписанные кадры WebSocket
  vectors/approval_hash.json      # этап 4: объект операции → op_sha256
  vectors/ssh_pubkey.json         # этап 6: X9.63 → строка OpenSSH

  vectors/pages/{valid,invalid}/  # этап 5: страницы и ожидаемые тексты ошибок
```

**Как клиент получает контракты** — копия с проверкой хеша (вариант Ильи «копия + хеш в тестах»; согласовано с агентом iOS):

- В RHServer лежит `contracts/MANIFEST.sha256`: sha256 каждого файла `contracts/` в формате `sha256sum` (`<hex>  <путь относительно contracts/>`, сортировка по пути, сам манифест не включается); корневой хеш = sha256 байт файла манифеста. Генерирует `scripts/contracts_manifest.py`; тест сервера падает, если манифест не совпадает с файлами — значит, контракт нельзя изменить, не обновив манифест.
- В RHClient — копия `contracts/` целиком (с манифестом) и `contracts/UPSTREAM`: SHA коммита RHServer и корневой хеш. Обновление только скриптом `scripts/sync-contracts.sh <sha>`, отдельным коммитом «sync contracts @<sha>».
- Тест клиента пересчитывает хеши файлов копии и сверяет с манифестом и с корневым хешем в `UPSTREAM`; любое расхождение — красный тест. Так копия не может молча разъехаться с оригиналом.
- В CI клиента (где есть сеть) дополнительно: манифест на коммите `UPSTREAM` в RHServer совпадает с копией.
- Сабмодуль — запасной вариант, если Илья предпочтёт: он сложнее для Xcode и клонов (`--recursive`, доступ к приватному репо из CI).
- Изменения контракта — только PR в RHServer с ревью агента iOS; клиент подтягивает новую версию осознанно, синком на конкретный SHA. Каждое изменение — запись в `contracts/CHANGELOG.md`.
- Главная часть контракта — тест-векторы: тесты обеих сторон гоняются по одним и тем же файлам, расхождение сериализации ловится в первый день, а не на pairing.

**Формат векторов** — JSON, одинаковый для обеих сторон:

- `jcs.json`: `[{ "name", "input": "<сырой JSON-текст строкой>", "expected": "<канонический текст>", "expected_sha256", "scope": "protocol" | "full" }]`. Вход строкой, чтобы парсеры языков не влияли. `protocol` обязателен обеим сторонам (строки с юникодом и экранированием, целые, массивы, вложенность, сортировка ключей по UTF-16, включая не-ASCII); `full` — числа по ES6, включая примеры RFC 8785 (обязателен серверу).
- `ecdsa.json`: `{ "name", "pub_x963_b64", "message_b64", "sig_der_b64", "valid" }` — включая битый DER, чужой ключ и одну подпись настоящего Secure Enclave (от iOS, этап 1). High-S сервер принимает (так ведёт себя `cryptography`; Security.framework может выдавать обе формы) — вектор с high-S помечен `valid: true`.
- `request_build.json`: `{ "name", "priv_scalar_b64", "device", "key", "nonce", "ts", "exp", "op", "body_b64", "expected_auth_b64", "expected_auth_text" }` — клиент собирает `X-RH-Auth` и сверяет байт-в-байт; подпись недетерминирована, её клиент проверяет через verify.
- `signed_requests.json`: `{ "name", "registry", "now", "used_nonces", "issued_nonces", "request": { method, path, headers, body_b64 }, "expect": "accept" | { "reject": "<code>" } }`.
- `server_sig.json`: `{ "name", "core_pub_x963_b64", "request_nonce", "status", "body_b64", "sig_der_b64", "valid" }` — включая подмену статуса и тела, ответ на challenge (`nonce` = выданный nonce из тела), отказ challenge (`nonce: ""`) и ответ pair (`nonce` = код из QR).

### Протокол: конкретизация SPEC §4 (входит в `contracts/` этапа 1, согласуется с iOS)

Это уточнения формата, а не изменение решений §4; если агент iOS или Илья видят в них отход от SPEC — обсуждаем до кода.

- Публичные ключи: X9.63 uncompressed (65 байт, так отдаёт `SecKeyCopyExternalRepresentation`), base64 стандартный с паддингом. Ключ ядра — тоже P-256.
- `device_id` = первые 32 hex-символа `sha256(normal_pub_x963)`; вычисляет клиент, ядро сверяет при pairing. Выбран вместо UUID: id привязан к ключу, его нельзя занять чужим ключом, и не нужно отдельно хранить его на телефоне.
- `ts`, `exp`: `YYYY-MM-DDTHH:MM:SSZ`, UTC, без долей секунды. `exp − ts ≤ 60 с`.
- `body`: sha256 (hex, lowercase) сырых байт тела; для пустого тела — sha256 пустой строки.
- Подписываются байты JCS-объекта из §4.3; `X-RH-Auth` = base64 этих байт. Ядро разбирает `X-RH-Auth`, перекодирует в JCS и требует побайтного совпадения (защита от неканонического ввода).
- `op` закреплён за эндпоинтом (`x-rh-op`), уровень ключа — за `op` (`x-rh-key`). Чужой `op` — отказ `op_mismatch`.
- `POST /v1/challenge` `{ "device": "<id>" }` — без подписи (подписать ещё нечем), отказ для неизвестного и отозванного устройства (§4.5). Ответ: `{ "nonce", "expires", "server_time" }`.
- `POST /v1/pair`: в роли nonce — одноразовый код из QR; подписи `X-RH-Sig` (normal) и `X-RH-Sig-Critical` (critical) над одним объектом; тело — имя устройства, три публичных ключа (`normal`, `critical`, `ssh`) и необязательное `replaces: <прежний device_id>` (клиент хранит его в Keychain, он переживает переустановку). Запрос держится открытым до `y`/`n` в терминале или до истечения кода (≤ 5 минут): `200` с подписью ключом ядра из QR, либо `403 pair_rejected` / `403 bad_pair_code`. Ответ несёт `device_id` и необязательное `ssh_host_keys` (строки `/etc/ssh/ssh_host_*_key.pub`, они world-readable) — чтобы клиент SSH проверял ключ хоста без вопроса при первом подключении; **утверждено Ильёй 2026-10-19** (вариант A), поле с этапа 1.
- Строка pairing (QR и буфер обмена в симуляторе): `rhpair:` + base64url без паддинга (JCS `{"v":1,"url":"https://<имя MagicDNS>:<порт>","core_key":"<b64>","code":"<b64>","exp":"<ts>"}`). В симуляторе — из буфера обмена или аргумента запуска `-RHPairing <строка>`.
- Отпечаток устройства (терминал и экран pairing на телефоне): первые 16 hex `sha256(JCS {"normal","critical","ssh"})` группами по 4.
- Отказы: HTTP 401/403 и `{"error":{"code","message"}}`, коды: `malformed_auth`, `unknown_device`, `revoked_device`, `wrong_key_level`, `op_mismatch`, `nonce_unknown`, `nonce_used`, `nonce_expired`, `expired`, `clock_skew`, `body_mismatch`, `bad_signature`, `bad_pair_code`, `pair_rejected`, `peer_mismatch` (whois, §3.3). Код нужен клиенту, чтобы отличать **Auth error** от **Pairing lost** (§4.2).
- В подписываемых объектах только строки и целые; дробные числа запрещены (ядро отвечает `malformed_auth`).
- `X-RH-Server-Sig`: DER-подпись ключом ядра (base64) над JCS `{"v":1,"nonce":"<nonce запроса>","status":<HTTP-код>,"body":"<sha256 hex тела ответа>"}`; статус внутри, чтобы 4xx нельзя было выдать за 2xx. Подписываются и ответы-отказы. У challenge в запросе nonce нет: подписывается выданный nonce, при отказе — `""`; у pair — код из QR.
- WebSocket: upgrade-запрос несёт те же `X-RH-Auth`/`X-RH-Sig` с `op: "ws.open"`; сокет привязан к устройству; при отзыве устройства ядро закрывает его сокеты. Кадр сервера: `{"seq":<n>,"type":"…","data":{…},"sig":"<b64>"}`, `seq` растёт с 1 в пределах соединения (дедупликация и контроль пропусков), `sig` — ключом ядра над JCS `{"v":1,"nonce":"<nonce ws.open>","seq":<n>,"body":"<sha256 hex JCS {seq,type,data}>"}`. После переподключения клиент берёт состояние через REST, история по сокету не досылается. Схема событий — `contracts/api/events.schema.json`.
- Чтения могут идти `GET` (тело пустое, `body` = sha256 пустой строки); подпись и challenge — как для всех запросов.

### Внутренний канал rh-agent ↔ rh-core

Не входит в `contracts/` (клиент его не видит), описывается в `docs/`. Unix-socket в каталоге данных ядра, JSON Lines (запрос/ответ + события). ## Этап 1. Доверие

**Задачи**
1. Крипто (`rh_common/crypto.py`): загрузка X9.63, проверка DER-подписи, ключ ядра (генерация при первом старте, хранение в каталоге данных с правами 600), подпись ответов.
2. `contracts/` этапа 1 (отдельный PR первым): эндпоинты `challenge`, `pair`, `ping`, `status`, `devices.list`, `devices.revoke`, `ws.open`; события `device.revoked`; векторы `ecdsa`, `request_build`, `signed_requests`, `server_sig`, `pairing`.
3. Хранилище SQLite (`rh_core/store.py`) с миграциями: устройства (id, имя, ключи по уровням, дата pairing, статус), nonce (выданные/использованные, TTL).
4. Проверка запроса — одна функция-middleware с полным перечнем отказов §4.3 и кодами выше; каждый отказ и каждый принятый запрос — в журнал.
5. Журнал ядра (`rh_core/journal.py`): JSON Lines, файл на день, поле `prev` (sha256 предыдущей записи, цепочка через границу файлов), fsync; `rhcore journal verify` проверяет цепочку.
6. `rhcore pair`: одноразовый код (5 минут), QR в терминале + строка pairing текстом, ожидание запроса, показ отпечатка, подтверждение `y`, запись в реестр; повторный pairing (§4.2): если в запросе есть `replaces`, терминал показывает «заменяет устройство X» и отзывает его тем же `y`; если нет — терминал показывает активные устройства с тем же именем, и тем же `y` они отзываются. Ключ `ssh` сохраняется в реестре с этапа 1; добавление в `~/.ssh/authorized_keys` — этап 6, без повторного pairing.
7. `rhcore devices list | revoke <id>`, `rhcore dev up` (dev-режим, §9.1), `rhcore serve` (HTTPS на интерфейсе Tailscale).
8. Привязка к сети (§3.3): адрес слушания — только 100.x / MagicDNS из конфига, не 0.0.0.0; сертификат через `tailscale cert`; сверка отправителя через LocalAPI whois (несовпадение — отказ `peer_mismatch` и запись в журнал). В dev-режиме whois отключён.
9. WebSocket: `ws.open` по подписанному upgrade, реестр соединений по устройству, закрытие при отзыве.

**Тесты** (все — и в unit, и на векторах `signed_requests.json`)
- Отклоняются и видны в журнале с причиной: повтор nonce, просроченный nonce, `exp` в прошлом, расхождение часов > 120 с, чужой ключ, неизвестное устройство, отозванное устройство (включая challenge), неверный уровень ключа для `op`, изменённое тело, неканонический `X-RH-Auth`, чужой `op`.
- Принимается корректный `ping`; ответ подписан и проходит проверку по ключу ядра.
- Журнал: цепочка верна; правка любой записи задним числом ловится `journal verify`.
- Pairing: неверный/просроченный/повторный код; подпись только одним ключом; повторный pairing отзывает старую запись.
