## Test vectors

Fixed inputs and exact expected outputs. Tests on both sides run over the same files; a mismatch in serialization shows up as a red test on day one, not at pairing.

`vectors/jcs.json`: `input` is raw JSON text (a string, so no language parser touches it first), `expected` is the canonical text, `expected_hex` its UTF-8 bytes, `expected_sha256` their hash. Vectors with `"expect_error": true` (no `expected*` fields) must be rejected. The root is an object: `{"description", "version", "vectors": [...]}`.

- `scope: "protocol"` — strings, integers, arrays, nesting, key order by UTF-16 code units. This is everything a signed object contains. **Both sides must pass.**
- `scope: "full"` — doubles (ECMAScript formatting, RFC 8785 Appendix B) and invalid input. Server only; signed objects never contain fractional numbers.

### Stage 1 vectors

All keys are fixed test keys; private scalars are included so either side can sign. Signatures are RFC 6979 (deterministic) only so the files are stable.

- `ecdsa.json` — public key + message + DER signature → `valid`. High-S is valid; truncated or raw r‖s is not.
- `request_build.json` — fields → `expected_auth_text` / `expected_auth_b64` byte for byte; `sig_der_b64` verifies.
- `signed_requests.json` — `fixture` (registry, nonces, pairing codes, `now`) + requests → `accept` or `reject` with `code` and HTTP `status`; `nonce_consumed` for non-pair requests. Every vector is evaluated against the untouched fixture.
- `server_sig.json` — what `X-RH-Server-Sig` covers, valid and tampered cases, with the message text to rebuild.
- `pairing.json` — pairing strings → fields, or `expect_error`; `fingerprints`.
- `ws_frames.json` — WebSocket frames → `valid`.

Vectors are generated by `scripts/gen_vectors.py` from cases listed in it; a server test fails if the committed files differ from the generator output.

## The copy in RHClient

RHClient keeps a full copy of this folder plus `contracts/UPSTREAM` with the RHServer commit SHA and the root hash. The root hash is the sha256 of the bytes of `MANIFEST.sha256`. A client test recomputes the hashes of its copy and goes red on any difference, so the copy cannot drift silently.

`MANIFEST.sha256` uses `sha256sum` format: `<hex>  <path relative to contracts/>`, sorted by path, the manifest itself excluded. Regenerate with `uv run python scripts/contracts_manifest.py`; `--check` fails when it is stale.

## Changing a contract

1. PR in RHServer that changes `contracts/`, updates `MANIFEST.sha256` and adds a line to `CHANGELOG.md`.
2. The iOS agent reviews it; the owner merges.
3. RHClient syncs to that SHA on purpose, in a separate commit `sync contracts @<sha>`.

Both sides may start work against a pinned SHA before the merge.
